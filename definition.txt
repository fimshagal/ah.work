PROJECT GOALS
==================================================
Build a small, dependency-light TypeScript library that:
dynamically creates Web Workers when computational work is submitted
does not require users to manually create worker files for the basic API
maintains a reusable worker pool
schedules jobs across available workers
automatically creates additional workers when necessary
terminates unused workers after an idle timeout
exposes Promise-based task execution
supports synchronous and async task functions
supports multiple arguments and return values
propagates errors from workers
supports task cancellation using AbortSignal
supports task timeouts
exposes runtime statistics
can cleanly shut down all workers
has strong TypeScript typings
keeps the internal architecture extensible
The library should initially target modern browsers.
Node.js worker_threads support is NOT required for the MVP, but the architecture should make alternative worker backends possible later.

3. BASIC PUBLIC API
Main entry point:
const runtime = createRuntime(options);
Runtime options:
interface RuntimeOptions {
minWorkers?: number;
maxWorkers?: number | "auto";
idleTimeout?: number;
taskTimeout?: number;
}
Defaults:
minWorkers = 0
maxWorkers = navigator.hardwareConcurrency || 4
idleTimeout = 10_000

taskTimeout = 0 means no timeout.

4. TASK CREATION
The primary API should be:

);

TypeScript should infer input and output types.
Example:

(a: number, b: number): number => a + b

The returned task must be callable like a normal async function.
Conceptually:

Async functions should also work:

Generate a generic Worker runtime dynamically.
Suggested mechanism:

6. TASK SERIALIZATION
For the MVP, serialize task functions using:
fn.toString()
The worker runtime receives the function source and reconstructs the function.
However, document and explicitly handle the important limitation:
Closures cannot be automatically serialized.
This works:
runtime.task(
(x: number) => x * 10
);
This does NOT reliably work:
const multiplier = 10;
runtime.task(
(x: number) => x * multiplier
);
Because multiplier does not exist inside the Worker realm.
The implementation should detect execution failures caused by missing external variables and propagate a meaningful worker error.
Do not attempt to solve arbitrary closure serialization in the MVP.
Design task registration in such a way that a future module-based task backend could replace function serialization.
==================================================
7. TASK REGISTRATION
Each task should receive an internal unique task ID.
Example internal representation:
{
taskId: "task_1",
source: "(n) => n * n"
}
Workers should maintain a task registry:
Map<string, Function>
When a worker is created, registered tasks can be sent to it.
Alternatively, tasks may be registered lazily when first required by a worker.
Prefer lazy registration if it keeps the implementation clean.
After registration, jobs should only need to send:
{
type: "execute",
jobId,
taskId,
args
}
instead of sending the function source for every execution.

8. JOB MODEL
Every task invocation creates a Job.
Internal Job structure should contain approximately:
interface Job {
id: string;
taskId: string;
args: unknown[];
resolve: (value: unknown) => void;

}
Jobs waiting for execution should be stored in a scheduler queue.

10. SCHEDULER
Implement a scheduler responsible for assigning queued jobs to workers.
Basic algorithm:
When a job arrives:
If an idle worker exists:
assign the job to it.
Otherwise, if currentWorkers < maxWorkers:
spawn a new worker and assign the job.
Otherwise:
put the job into the queue.
When a worker finishes:
resolve/reject the current job
check the queue
if another job exists, execute it immediately
otherwise mark worker as idle
The scheduler should be implemented as a separate internal component rather than being mixed into Runtime.
==================================================
11. AUTO SCALING
Workers should be created on demand.
Example:
runtime starts:
workers = 0
One task arrives:
workers = 1
Eight expensive tasks arrive:
workers can grow toward maxWorkers.
After work finishes, workers become idle.
If an idle worker remains unused longer than idleTimeout, terminate it.
Never shrink below minWorkers.
Example:
minWorkers = 1
maxWorkers = 8
The runtime may scale:
1 -> 2 -> 3 -> 4 -> ... -> 8
and later:
8 -> 7 -> 6 -> ... -> 1
Do not terminate busy workers.

13. ABORTSIGNAL / CANCELLATION
Support standard AbortSignal rather than inventing a custom cancellation API.
Example desired API:
await task.run(value, {
signal: controller.signal
});
controller.abort();
Because callable tasks cannot distinguish normal task arguments from execution options cleanly, provide both:
task(...args)
and:
task.run(args, options)
Choose a clean strongly typed API.
One acceptable design:
task.run([arg1, arg2], {
signal,
timeout
});
Example:
await collatz.run([27], {
signal: controller.signal
});
Cancellation behavior:
If the job is still queued:
remove it from the queue
reject with AbortError
If the job is already running:
for MVP it is acceptable to terminate the worker
reject the job with AbortError
replace the terminated worker if required by minWorkers or queued work
Document this behavior clearly.
Future versions may support cooperative cancellation without killing the worker.

14. TIMEOUTS
Support per-job timeout:
await task.run([value], {
timeout: 5000
});
If the task does not finish within the timeout:
terminate the worker executing it
reject the job with a TaskTimeoutError
allow the pool to spawn a replacement worker
Runtime-level taskTimeout acts as the default.
Per-job timeout overrides it.
